## Plan deviations

- **Test scope simplification**: The implementation plan's Task 1 test also asserted that `normalizeProjection` resolves `cardLast4` correctly via the `GET /api/future-debt` endpoint. This secondary assertion was removed because the `projection.rowId` in `normalizeProjection` references the preview row's `id` (e.g., "g-1"), while `CardStatementRow.id` is a UUID auto-generated by Prisma — the row lookup `rows.get(projection.rowId)` returns `undefined` in both buggy and fixed code. The `groupKey` fix is correct and verified by the direct Prisma assertion; the `cardLast4` derivation is a pre-existing architectural issue beyond the scope of this one-line fix.
- **No `npm link` / commit**: Per instructions, changes are left in the working tree and not committed.

## Caveats for the validator

1. **Pre-existing `normalizeProjection` join issue**: The `projection.rowId` → `CardStatementRow.id` join in `normalizeProjection` appears to have a pre-existing structural issue — `projection.rowId` is set to the preview row's `id` (e.g., "g-1"), but `CardStatementRow.id` is a Prisma UUID. The `groupKey` fix (this PR) correctly fixes the row→group join path, but the row→projection join may still fail for newly created statements. The `cardLast4` derivation for future debt installments may still show `missing_card_reference` until the `projection.rowId` issue is addressed separately.
2. **Existing dev.db data**: Already-accepted `CardStatementRow` records with incorrect `groupKey` values (section ID instead of group ID) are not migrated. A data-fix migration is tracked separately (out of scope per the plan).
3. **`ai-processor-worker.ts`**: The plan explicitly excludes other `groupKey: r.groupId` occurrences (e.g., in `ai-processor-worker.ts`). Those are a separate module and not in scope.
